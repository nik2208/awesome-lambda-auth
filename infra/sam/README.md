# SAM quickstart

An auth service in your own AWS account: one HTTP API, one Lambda, one DynamoDB
table. `template.yaml` is a SAM template (`AWS::Serverless-2016-10-31`), but
**you do not need the SAM CLI** — the transform runs server-side in
CloudFormation, so the plain AWS CLI does the whole flow. The scripts below use
nothing else.

## Prerequisites

- **Docker**, to build the Lambda binary. The repo installs no Go toolchain on
  the host; `scripts/build-lambda.sh` compiles inside a pinned `golang` image.
- **AWS CLI v2**, with a named profile whose credentials can create IAM roles,
  Lambda functions, API Gateway APIs, DynamoDB tables, Secrets Manager secrets
  and an S3 bucket.

## What gets created

Inside the stack:

| Resource | Notes |
|---|---|
| `AWS::DynamoDB::Table` | Single table, `PK`/`SK` + one sparse GSI, on-demand billing with read/write ceilings, PITR on, TTL on `ttl`, streams `NEW_AND_OLD_IMAGES`. Key schema is `docs/spec/data-model.md` §2, not a guess. |
| `AWS::Serverless::Function` | `provided.al2023`, arm64, 512 MB, 10 s timeout. One function for the whole auth router — not function-per-route. |
| Its execution role | DynamoDB scoped to the table ARN and `…/index/GSI1`, plus `secretsmanager:GetSecretValue` on exactly the signing secret the function reads — one ARN by default. See below. |
| `AWS::Serverless::HttpApi` | Payload format 2.0. `$default` stage, so the API serves at the domain root. |
| `AWS::Logs::LogGroup` | `/aws/lambda/<stack>-auth`, 14-day retention by default. |
| `JwtSigningSecrets` | One `AWS::SecretsManager::Secret` holding a JSON document with **two** keys, `accessTokenSecret` and `refreshTokenSecret` — 64 characters each, generated by AWS. This is the only secret the function reads. |
| `JwtRefreshSecretSeed` | A second `AWS::SecretsManager::Secret` that exists only to make AWS generate the *second* random value. Not in the function's environment, not in its IAM policy, never read at runtime. [Why it exists.](#why-there-are-two-secret-resources-for-one-secret) |
| `IdpSigningKey` + `IdpSigningKeyAlias` | **Only when `EnableIdp=true` and `IdpKmsKeyId` is empty.** An `AWS::KMS::Key`, `KeySpec: RSA_2048`, `KeyUsage: SIGN_VERIFY`, plus `alias/<stack>-idp`. The private half never leaves KMS; the function is granted `kms:Sign` and `kms:GetPublicKey` on this one ARN, and `kms:GetPublicKey` on any ARN in `IdpPreviousKmsKeyArns` — nothing else in the account. **USD 1.00 per month** — see [Cost at rest](#cost-at-rest). |

Both secret resources are skipped when you supply both of `JwtAccessSecretArn` and
`JwtRefreshSecretArn`. The KMS key is skipped when you supply `IdpKmsKeyId`, and
never created at all while `EnableIdp` is `false`.

### Where the signing secrets live

Both HS256 keys live in **one** secret, as two keys of a JSON document:

```json
{ "accessTokenSecret": "…64 chars…", "refreshTokenSecret": "…64 chars…" }
```

The function's environment holds that secret's **ARN**, not its value, once per
knob with a different `#<jsonKey>` selector:

```sh
aws lambda get-function-configuration --function-name <stack>-auth \
  --profile <profile> --region <region> \
  --query 'Environment.Variables' | grep SECRET
#   "AWESOME_AUTH_JWT_ACCESS_SECRET_SECRETSMANAGER":  "arn:aws:secretsmanager:…#accessTokenSecret"
#   "AWESOME_AUTH_JWT_REFRESH_SECRET_SECRETSMANAGER": "arn:aws:secretsmanager:…#refreshTokenSecret"
```

The function fetches the secret itself at cold start, once per execution
environment, and caches it for that container's life — never per request. The
cache is keyed on the secret id with the selector stripped
(`internal/integration/aws/secrets.go`), so the two knobs above cost **one**
`GetSecretValue`, not two. That is the only reason the two keys share a secret;
see [Measured on a real deployment](#measured-on-a-real-deployment) for what it
bought.

That is the whole point of the `_SECRETSMANAGER` suffix: the unsuffixed
`AWESOME_AUTH_JWT_ACCESS_SECRET` is the *value*, is development-grade, and must
not appear in a deployed template. Anyone with `lambda:GetFunction` now learns
where the key lives — which they could learn from the stack anyway — and still
cannot sign a token without `secretsmanager:GetSecretValue` on that exact ARN.

**You never handle the value.** `GenerateSecretString` creates it inside AWS.
There is no command to run, nothing to paste, nothing in your shell history.

#### Why there are two secret resources for one secret

`GenerateSecretString` fills in exactly one key: `GenerateStringKey` names it and
`SecretStringTemplate` supplies the rest of the document as literal text. There
is no second generator. So the second random value comes from a second secret,
`JwtRefreshSecretSeed`, whose only job is to hold it, copied into the JSON
document with a secret-to-secret `{{resolve:secretsmanager:…}}` dynamic
reference at stack-create time.

The two values are independent 64-character strings drawn by AWS. Deriving one
from the other — HMAC, hash, a suffix — would have removed the second resource
and was rejected: two keys that are a pure function of each other are one key
wearing two names, and RS-1's "the two must differ" would hold in letter only.

What that costs, plainly:

- **Cost at rest does not improve.** Two secrets are still billed. Only cold
  start improves.
- **The refresh key exists in two places.** The seed is not in the function's
  environment and not in its IAM policy, so nothing about the *runtime* blast
  radius changes; the extra copy is reachable only by a principal with
  account-wide Secrets Manager read, who could read the real secret anyway.
- **You cannot delete the seed by hand.** CloudFormation re-resolves the dynamic
  reference every time it builds a changeset for the stack, and a missing seed
  fails the changeset.

The resolved value does not leak into CloudFormation: it appears in neither
`get-template --template-stage Original` nor `Processed`, nor in
`describe-stack-events`. That was checked on a real deployment, not assumed.

#### Bringing your own

One parameter, and no exposure either:

```sh
# a secret whose value is a bare string
./scripts/deploy.sh --profile <profile> --region <region> \
  --parameter JwtAccessSecretArn=arn:aws:secretsmanager:<region>:<account>:secret:my/jwt-AbCdEf

# a secret whose value is a JSON document — append the key
./scripts/deploy.sh --profile <profile> --region <region> \
  --parameter JwtAccessSecretArn=arn:…:secret:my/jwt-AbCdEf#accessTokenSecret \
  --parameter JwtRefreshSecretArn=arn:…:secret:my/jwt-AbCdEf#refreshTokenSecret
```

Both shapes work, and they mix freely — one knob on a bare-string secret and the
other on a key of a JSON secret is a supported combination. It must be an ARN,
not a name, because the same value is the IAM policy's `Resource` and a bare name
there is not a valid ARN; the `#` selector is stripped before the ARN reaches
IAM.

Supply **both** parameters and the stack creates no secrets at all. Supply only
one and the stack still generates `JwtSigningSecrets` for the other — you then
have two distinct secrets and cold start pays two fetches, which is the second
example above being worth the small extra effort.

#### Rotating

`aws secretsmanager put-secret-value` on `JwtSigningSecrets`; the next cold start
picks it up, with no redeploy. Tokens signed with the old value stop verifying,
which is what rotation means.

**The trade-off the one-secret layout makes is here, and it is real.** The secret
value is one JSON document, so `put-secret-value` replaces *both* keys at once:

- There is no "rotate the access key and leave refresh alone". Rotating one key
  means reading the document, changing one member and writing the whole thing
  back — a read-modify-write you have to get right, on a value you must not
  print. Two separate secrets each had a one-command rotation that touched
  nothing else.
- Writing the document means **you** produce the new material, so the "no human
  ever handles the value" property that `GenerateSecretString` gives you at
  create time does not survive a manual rotation. Generate it with
  `aws secretsmanager get-random-password --password-length 64 --exclude-punctuation`
  and pipe it, rather than inventing one.
- Rotating invalidates every access token *and* every refresh token in one step,
  so every session ends, rather than only the half you meant to rotate. If a
  staged rotation matters to you, keep two secrets: set `JwtAccessSecretArn` and
  `JwtRefreshSecretArn` to two of your own ARNs and accept the second fetch.
- `JwtRefreshSecretSeed` is *not* what you rotate. After stack creation nothing
  reads it; a rotation that updates the seed changes nothing and a rotation that
  updates `JwtSigningSecrets` leaves the seed stale on purpose.

Secrets Manager's own scheduled rotation (`AWS::SecretsManager::RotationSchedule`)
is not wired up by this template in either layout.

SSM SecureString works too — set `AWESOME_AUTH_JWT_ACCESS_SECRET_SSM_PARAMETER`
instead — but this template does not grant `ssm:GetParameter`, because nothing
in the default stack calls it. The statement to add is written out in the
template, next to the one that is granted.

Outside the stack, created by `scripts/deploy.sh`: a private, encrypted,
versioned S3 bucket named `awesome-lambda-auth-artifacts-<account-id>-<region>`
to upload the Lambda zip to. It is not stack-managed, so teardown only removes
it if you ask.

### The IAM policy is the point

The function's policy grants exactly the seven DynamoDB item actions the store
calls, on exactly two ARNs — the table and its one index — and nothing else. No
`Resource: "*"`, no `dynamodb:*`, no `Scan`, no `DescribeTable`, not even `ConditionCheckItem`,
because nothing in the current store puts a bare condition check into a
transaction. If you copy one thing out of this template into your own stack,
copy that block. A wildcard in an auth service's execution role is a bad example
that propagates.

The second statement is one action — `secretsmanager:GetSecretValue` — on
exactly the secrets the function reads, which on the default path is the single
`JwtSigningSecrets` ARN. Not even the `:*` suffix AWS documentation habitually
appends: a full ARN including the six-character suffix Secrets Manager
generates is an exact match, and the wildcard form would also match every
future secret whose name shares the prefix. `JwtRefreshSecretSeed` is
deliberately *not* in it — CloudFormation consumes the seed at create time and
the function never touches it, so granting a read would widen the runtime blast
radius for nothing. No `kms:Decrypt`, because the AWS-managed
`aws/secretsmanager` key needs no grant on the caller; a customer-managed key
does.

The delivery statements hold the line where their services allow it, and say so
where they do not:

* **`ses:SendEmail`** is scoped to one identity ARN — the verified domain or
  address the mail is sent *from*. A recipient is not an AWS resource, so the
  sender identity is the only thing there is to scope, and scoped to it this
  role can send as `no-reply@yourdomain` and as nothing else in the account.
  One action: no `SendRawEmail` (the transport sends simple content),
  no `SendTemplatedEmail` (templates render in-process), no `ListIdentities`.
* **`sns:Publish`** cannot be scoped by `Resource` at all. Publishing to a phone
  number has no ARN, so `Resource: "*"` is the only Resource form that grants it
  — and that same statement would let the function publish to every SNS topic in
  the account, including topics that feed a Lambda, a queue or a webhook. The
  policy therefore uses `NotResource: arn:aws:sns:*:*:*`, which allows the action
  against everything that is not an SNS topic: text messages to a handset, yes;
  anything with a topic ARN, no.

Both statements are absent from the role entirely unless their half is
configured — `MailerFromAddress` for mail, `EnableSmsDelivery` for SMS.

There are three more `secretsmanager:GetSecretValue` statements, and each
follows the signing-secret one exactly: one present only when
`EmailDeliveryWebhookSecretArn` is set, one only when `ClaimsWebhookSecretArn`
is set, and one only when an OAuth provider is configured, each scoped to the
ARNs actually named with any `#<jsonKey>` selector stripped, because the
selector is the function's and the resource is the secret. Three statements
rather than one with every ARN on it, so that a stack with one webhook grants
nothing for the other; and a stack with one provider grants one read, while a
stack with none grants nothing for OAuth at all.

The last two statements are the identity provider's, present only when
`EnableIdp` is `true`. The first carries two actions on the current key ARN:

* **`kms:Sign`** produces the RS256 signature of every token the IdP issues. The
  request carries the 32-byte SHA-256 of the token's signing input and nothing
  else (`MessageType: DIGEST`), so the claims — the subject's id, their email —
  never reach the service.
* **`kms:GetPublicKey`** is what the JWKS document is built from, once per
  execution environment.

No `kms:CreateKey`, no `kms:ScheduleKeyDeletion`, no `kms:PutKeyPolicy`: an auth
router that can delete its own signing key, or grant a third party the use of it,
is a bad example that propagates. No `kms:Encrypt` or `kms:Decrypt` either —
a `SIGN_VERIFY` key would refuse them anyway, so granting them would say
something untrue about what the function does.

The second statement exists only while `IdpPreviousKmsKeyArns` is non-empty, and
it grants **`kms:GetPublicKey` and nothing else** on those ARNs. A retired key is
published in the JWKS document so that tokens it signed keep verifying, and the
function builds that document by calling `GetPublicKey` on every listed id at
cold start — so a rotation whose policy was not extended fails the init with
`idProvider.kmsPreviousKeyIds: … AccessDeniedException`, not one bad request.
That is why the ARNs are a stack parameter rather than a `ConfigFile` key: the
one value sets `AWESOME_AUTH_IDP_KMS_PREVIOUS_KEY_IDS` and extends the policy
together, so the two cannot drift. `kms:Sign` stays on the current key alone — a
key that has been retired must not be able to mint anything.

**`IdpKmsKeyId` and `IdpPreviousKmsKeyArns` must be key ARNs, not alias ARNs**,
and the pattern on `IdpKmsKeyId` enforces it. IAM evaluates KMS actions against
the key's own ARN: a statement whose `Resource` is an alias matches nothing at
all, and the failure shows up as `AccessDeniedException` on the first token, long
after a deploy that looked successful. The function's environment can still name
the current key however you like — an alias is fine there — but the two values
come from the same parameter, so the ARN is what both get.

## Credential delivery

Five routes mint something that has to reach a person: `/magic-link/send`,
`/forgot-password`, `/send-verification-email`, `/change-email/request` and
`/sms/send`. Mail goes through **Amazon SES v2**, text messages through an
**SNS publish straight to the recipient's number**.

| Parameter | Effect |
|---|---|
| `MailerFromAddress` | The `From` address, and the switch: empty wires no mail transport. It must be a verified SES identity in this region, or an address under a verified domain. |
| `MailerFromName` | Display name on the `From` header, and the application name the built-in templates greet with. Empty falls back to the sender's domain. |
| `MailerIdentity` | Which SES identity the IAM grant names. Defaults to the domain of `MailerFromAddress`. Set it when the *address* is what was verified rather than the domain. |
| `MailerDefaultLang` | `en` or `it`; selects the built-in template set. |
| `EnableSmsDelivery` | `true` wires SNS and grants `sns:Publish`. Off by default. |

**Configure neither and nothing breaks.** `/magic-link/send` answers 500
`EMAIL_NOT_CONFIGURED` and `/sms/send` answers 500 `SMS_NOT_CONFIGURED`, because
neither can put the credential in its response body; the other three answer 200
and mail nothing. That is what the reference does with no email block, and a
deployment serving bearer clients that never touch those routes is unaffected.

Two things about SMS are outside this stack and will bite otherwise: a new
account is in the **SNS SMS sandbox** and can only text numbers it has verified,
and stored numbers must be **E.164** (`+<country><number>`) — SNS routes nothing
else, and the transport refuses a number without a `+` rather than letting SNS
answer with a generic `InvalidParameter`.

### Why the mailer endpoint in the environment is a placeholder

`config-schema.md` §1.5 marks `email.mailer.endpoint` required, because in the
reference a mailer *is* an HTTP endpoint you POST to with an `X-API-Key`. SES is
neither: it is called through the AWS API and authorised by the execution role.
So the template sets the required knob to a deliberately unreachable placeholder
and the function reports it — along with `email.mailer.apiKey`, `sms.endpoint`,
`sms.apiKey`, `sms.username` and `sms.password` — as a configured knob it cannot
honour, by dotted path, in the cold-start log:

```
{"level":"WARN","msg":"configured knob is not wired to the auth core",
 "path":"email.mailer.endpoint",
 "problem":"this build delivers mail through Amazon SES, which is called through the AWS API and not by posting to a URL, …"}
```

Nothing is silently ignored, and no credential has to be invented: there is no
mailer API key and no SMS gateway password in this stack, which also retires the
credentials-in-URL hazard `config-schema.md` §1.6 records for the SMS gateway —
there is no URL.

The report also covers the case where a credential is set and its block is *not*.
`email.mailer.apiKey`, `sms.apiKey`, `sms.username` and `sms.password` are the
knobs that live in Secrets Manager, so they are the ones a hand-written
environment carries; `email.mailer.from` and `sms.endpoint` are the switches, and
they are the ones that get forgotten. Set a credential without its switch and
delivery is simply off — so the log names the missing switch rather than only
calling the credential unused:

```
{"level":"WARN","msg":"configured knob is not wired to the auth core",
 "path":"sms.password",
 "problem":"SNS authorises the call with the Lambda execution role's sns:Publish permission, …, and this deployment sends nothing through that half at all",
 "remedy":"sms.endpoint is unset, so no SMS transport is wired at all and POST /sms/send answers 500 SMS_NOT_CONFIGURED: set it to turn SMS delivery on, or delete the credential"}
```

## Email flows

Three more parameters decide where an emailed link points and who delivers it.

| Parameter | Effect |
|---|---|
| `EmailSiteUrls` | Comma-separated absolute URLs. The first is the canonical site every emailed link is built on; all of them, together with `AllowedOrigins`, form the allowlist a request's `Origin` or `Referer` is matched against. Empty falls back to `PublicUrl` and honours no request origin. |
| `EmailDeliveryWebhookUrl` | An https receiver that is POSTed a signed JSON copy of every credential delivery **instead of** SES and SNS: with it set, all five credential seams go there and nothing is mailed or texted for them. |
| `EmailDeliveryWebhookSecretArn` | The Secrets Manager ARN of the key that signs those requests. **Required with the url**, and refused without it. |

The signature is `X-Webhook-Signature: sha256=<hex HMAC-SHA256 of the body>`,
the family's outbound-webhook convention, so a receiver already written for the
tools router's webhooks verifies these the same way. The secret is required
because the body of every request *is* a credential: a receiver that cannot
verify the signature cannot tell a replayed or forged delivery from a real one.
Nothing is generated for you — the receiver has to hold the same key.

`email.templatesDir` has no parameter here and is not an oversight: it names a
directory inside the artifact, which `scripts/build-lambda.sh` bakes and the
configuration document points at (`ConfigFile`). See
[`docs/config-reference.md`](../../docs/config-reference.md) §5 for the file
layout and for the rule that the store always wins over the directory.

**Templates do not work on a stack deployed from this template, and that is a
build limitation rather than a template one.** `email.templatesDir` requires
`stores.enable.templates`, which requires a driver whose store provides a
`TemplateStore`; `internal/store/dynamodb` has none in this build, and this
template deploys nothing else. Turning the switch on refuses the cold start by
name, so the failure is loud rather than silent, but there is no parameter here
that makes it work — the built-in `en`/`it` templates render until the DynamoDB
template store lands. `docs/config-reference.md` §5.3 has the whole picture.

## Second factor and token claims

Four parameters, and only the first applies to every stack.

| Parameter | Effect |
|---|---|
| `TotpIssuer` | `AWESOME_AUTH_2FA_APP_NAME` — the name an authenticator app prints above the six digits, and the issuer in the `otpauth://` URI `POST /2fa/setup` returns. Default `awesome-node-auth`, the reference's own; set it to the product name your users know. Empty is refused at start. |
| `ClaimsWebhookUrl` | An https endpoint asked for extra token claims on every mint and on `GET /me`. Empty disables it. |
| `ClaimsWebhookTimeoutMs` | One request, connect to last byte. Default 2000. A login is waiting on it inside the invocation, so keep it well under `Timeout`. |
| `ClaimsWebhookSecretArn` | The Secrets Manager ARN of the key that signs those requests. **Required with the url**, and refused without it. |

The claims webhook is POSTed `{"user": <the profile as GET /me renders it>}`
and answers `{"claims": {…}}`, signed with the same
`X-Webhook-Signature: sha256=<hex HMAC-SHA256 of the body>` convention the
delivery webhook uses. The secret is required for a different reason than the
delivery webhook's: the request body is your users' profiles and the answer
decides what the token authorises, so an unsigned receiver can neither tell your
deployment's question from anyone else's nor be told apart from a receiver that
is not it.

**It fails closed.** A failure, a timeout, a non-2xx, or a body that is not a
claims object aborts the mint, and login, refresh and 2FA step-up answer
`500 {"error":"Internal server error"}`. Budget for that when you decide whether
the receiver belongs in the login path at all. `GET /me` is the exception: it
answers without `customClaims` rather than failing.

**A session is two tokens and the hook runs per token, so one login is two
requests** and one `GET /me` is one. Every other authenticated route is zero.

`security.jwt.extraClaims` has no parameter here, for the reason
`email.templatesDir` has none: it is a mapping table, which an environment
variable cannot carry. It arrives in the configuration document (`ConfigFile`);
see [`docs/config-reference.md`](../../docs/config-reference.md) §6.

## OAuth providers

Four parameters, two providers, and one thing you do **not** supply.

| Parameter | Effect |
|---|---|
| `OAuthGoogleClientId` | The client id from the Google Cloud console. Empty switches Google sign-in off and `GET <ApiPrefix>/oauth/google` answers the reference's `404 {"error":"Google OAuth not configured"}`. |
| `OAuthGoogleClientSecretArn` | Secrets Manager ARN of the client secret. **Required with the client id**, supplied rather than generated — the value comes from the provider's console. `#<jsonKey>` selects one key of a JSON secret. |
| `OAuthGithubClientId` / `OAuthGithubClientSecretArn` | The same pair for GitHub. |

The thing you do not supply is the **callback URL**. It is derived —
`<PublicUrl><ApiPrefix>/oauth/<provider>/callback` — and that is the URL to
register with the provider. A URL the operator typed and a URL the function
serves that disagree is a flow that dead-ends at the provider's `redirect_uri`
check, so there is nothing to be gained by letting them differ. Because the
derived value has to byte-match the registration, `PublicUrl` is constrained to
a bare origin (`https://auth.example.com`, no path, no trailing slash) and
`ApiPrefix` to non-empty segments — otherwise
`https://auth.example.com/` + `/auth` would produce a double slash and every
callback would be rejected by the provider.

The other thing you do not supply is the **linked-accounts store**. Setting a
client id also sets `AWESOME_AUTH_STORES_ENABLE_LINKED_ACCOUNTS=true`, because
that store is where the callback binds a provider identity to an account: with
it off the authorization redirect is still sent and the person still consents,
and then the callback answers `501 {"error":"Feature not supported by the
configured stores"}`. Refuse-to-start rule RS-11 refuses that combination, so
without this line a provider-configured stack would not start at all. It costs
nothing at rest — the rows live in the one table this stack already creates.

Its sibling, `stores.enable.pendingLinks`, is **not** set for you, because it is
a decision rather than a consequence. It buys two things: the single-use state
nonce (without it a captured `state` stays replayable for the whole of its TTL,
which is the reference's own behaviour, and the cold-start log says so), and the
`onEmailMatch: conflict` flow, whose stash lives there — RS-11 refuses that mode
without the store. Both are document-level knobs, so turn it on in `ConfigFile`:
`{"stores": {"enable": {"pendingLinks": true}}}`.

`Rules` refuse, at changeset time, the parameter combinations whose cold start
would then fail. One is unconditional, because the value has no document
equivalent — this template is what consumes it:

* a provider without `PublicUrl` — there is no origin to derive the callback
  from, and it cannot be defaulted to this stack's own execute-api URL (that is
  the circular dependency in the troubleshooting section below).

The rest also require `ConfigFile` to be empty, because a `Rule` can read
parameters and nothing else — it cannot see inside the configuration document,
where each of these knobs is equally at home. With a document supplied they step
aside and the cold-start rules do the checking, which is the only place both
sources are visible:

* a provider without a redirect allowlist — `EmailSiteUrls` or `AllowedOrigins`
  must name at least one origin, because the callback answers with a session in
  a `Set-Cookie` and decides where to send the browser from the origin inside
  the signed state; with nothing allowlisted, any origin that state names would
  be honoured (RS-11, `docs/spec/reference-issues.md` N1). A document may supply
  the same list under `email.siteUrls` or `http.cors.origins`;
* a client id with no secret ARN — an incomplete provider, unless the document
  references the secret itself as `{"secretsManager": …}`.

One more is unconditional in the other direction: a secret ARN with no client id
**parameter** is a secret nothing reads, whatever the document says, because the
`_SECRETSMANAGER` variable that would consume it is emitted only when the
parameter client id is set.

**A generic (non-Google, non-GitHub) provider has no parameters here.** It needs
three endpoints, a scope and usually a profile map, which is more structure than
a flat parameter list carries: configure it in the JSON configuration document
(`ConfigFile`), where every knob of `config-schema.md` §1.7 is available and its
client secret is a `{"secretsManager": …}` reference resolved the same way.
`docs/config-reference.md` §8 has the worked example.

## Cost at rest

Idle, with no traffic and an empty table, this stack costs roughly **$0.80 a
month** (**$1.80** with `EnableIdp=true`, which adds a KMS key — see below), and
all of it is the two Secrets Manager secrets at $0.40 each —
`JwtSigningSecrets` and the `JwtRefreshSecretSeed` that generated half of it.
Collapsing the two signing keys into one secret bought a faster cold start, not
a smaller bill; the seed still has to exist. Every other resource is either free
at rest or billed per request:

- DynamoDB on-demand: no hourly charge. Storage ~$0.25–0.31 per GB-month
  depending on region, plus about the same again for PITR. An empty table is
  effectively free.
- Lambda, HTTP API, DynamoDB streams (enabled but unconsumed): $0 when idle.
- CloudWatch Logs: ~$0.50 per GB ingested and ~$0.03 per GB-month stored.
  Retention is capped at 14 days by default because never-expire is a bill that
  only grows.
- S3 artifact bucket: a few megabytes per deployed version. Cents.

Under traffic the shape is roughly $1 per million API requests, $0.20 per
million Lambda invocations plus GB-seconds, and $1.25 per million DynamoDB
writes / $0.25 per million reads. Those are order-of-magnitude figures from the
public pricing pages and vary by region — check the current numbers before
budgeting on them.

`MaxReadRequestUnits` / `MaxWriteRequestUnits` default to 200 each. That is a
deliberate cap: a credential-stuffing run against `/login` becomes a DynamoDB
bill before it becomes an outage. Raise it on purpose, and alarm on it.

### The identity provider's KMS key

`EnableIdp=true` with no `IdpKmsKeyId` adds one customer managed KMS key, and it
is the only resource in this stack with a fixed monthly charge that is not a
Secrets Manager secret:

| Item | Price | Note |
|---|---|---|
| The key | **USD 1.00 / month** | Billed whether or not it ever signs, and **billed for the whole deletion window too**: scheduling a key for deletion starts a 7-day countdown (`PendingWindowInDays`), and the key costs its dollar until the window closes. |
| `kms:Sign` | **USD 0.03 per 10,000 requests** | ≈ **USD 3.00 per million tokens signed**. RSA-2048 asymmetric operations are the cheap tier; RSA-3072/4096 and ECC are five times that, which is one reason the key is RSA-2048. |
| `kms:GetPublicKey` | same tier, negligible | Called **once per execution environment** — the public key is memoised for the life of the process — so a stack with a hundred concurrent environments pays for a hundred calls a day, not one per token. |

Latency: an RSA-2048 `Sign` adds single-digit milliseconds to the request that
mints a token. It is on the path of `/token` and of nothing else — `/login` and
`/refresh` sign HS256 in-process and never call KMS.

Rounded, at 1 000 000 OIDC tokens a month: **USD 4.00**. At zero traffic with the
IdP enabled: **USD 1.00**. Prices are eu-west-1 at the time of writing and vary
by region; check the current pricing page before budgeting on them.

If that dollar matters more than the property it buys, `idProvider.privateKey`
with a PEM in Secrets Manager costs USD 0.40/month instead — and hands the
function a key it can read, copy and leak. [docs/oidc.md](../../docs/oidc.md) §2
argues the trade; the stack defaults to neither, because `EnableIdp` defaults to
`false`.

**Rotating it is two deploys, and the first one is a policy change.** Create the
new key, set `IdpKmsKeyId` to it and `IdpPreviousKmsKeyArns` to the old ARN, and
deploy: the JWKS document then publishes both keys under their own `kid`, and the
same parameter that lists the old ARN is what grants the `kms:GetPublicKey` the
document is built with. One access-token lifetime later, clear
`IdpPreviousKmsKeyArns` and deploy again. Skipping the parameter and listing the
retired key in `ConfigFile` instead leaves the policy short and the function
fails its init — [docs/oidc.md](../../docs/oidc.md) §3 shows the error. Two keys
mean two monthly dollars until the old one is deleted.

**`EnableIdp` and `EnableResourceServer` are mutually exclusive.** They describe
opposite deployments — one mounts `POST <prefix>/authorize`, which takes an email
and a password; the other exists to guarantee that no route here takes a
credential — and the function refuses to start when both are on (rule
`IDENTITY`). CloudFormation cannot check that, so the stack deploys and then
every request 500s with the rule in the log. To publish a signing key for others
to verify against without logging anyone in, that is `EnableIdp` with no clients,
not the resource server.

## Deploy

```sh
# 1. build the artifact (arm64, `bootstrap` at the archive root, reproducible)
./scripts/build-lambda.sh

# 2. package + deploy. --profile and --region are required and have no defaults.
./scripts/deploy.sh --profile <your-profile> --region <your-region>
```

`--build` folds step 1 into step 2. The script prints the account it resolved
and asks for confirmation before it touches anything; `--yes` skips the prompt
for CI.

Under the hood it is just:

```sh
aws cloudformation package \
  --template-file infra/sam/template.yaml \
  --s3-bucket <bucket> --s3-prefix <stack> \
  --output-template-file dist/packaged.yaml \
  --profile <profile> --region <region>

aws cloudformation deploy \
  --template-file dist/packaged.yaml \
  --stack-name <stack> \
  --capabilities CAPABILITY_IAM CAPABILITY_AUTO_EXPAND \
  --profile <profile> --region <region>
```

`CAPABILITY_AUTO_EXPAND` is what lets CloudFormation run the SAM transform.

Validate a template edit without deploying:

```sh
aws cloudformation validate-template \
  --template-body file://infra/sam/template.yaml \
  --profile <profile> --region <region>
```

Note what that does **not** do: it checks the template document, not the
expanded stack, because the SAM transform has not run yet. It will catch a
syntax error or a bad intrinsic; it will not catch an invalid Lambda property.

### Smoke test

```sh
curl -sS "$(aws cloudformation describe-stacks --stack-name <stack> \
  --query "Stacks[0].Outputs[?OutputKey=='ApiEndpoint'].OutputValue" --output text \
  --profile <profile> --region <region>)/healthz"
```

Outputs are `ApiEndpoint`, `TableName` and `FunctionName`, plus `IssuerUrl` and
`JwksUrl` when `EnableIdp=true`. Auth routes live under
`<ApiEndpoint><ApiPrefix>`, i.e. `/auth` by default.

`JwksUrl` is built from the issuer and `IdpJwksPath`, which defaults to
`/.well-known/jwks.json`. Move the document with that parameter and the output
follows; move it with `idProvider.jwksPath` inside `ConfigFile` and
CloudFormation cannot see the change, so the output would name a URL that 404s —
the discovery document's `jwks_uri` is the authority either way.

## Measured on a real deployment

Numbers from a `$default`-stage stack in `eu-west-1`, arm64 / 512 MB, defaults
otherwise, read from CloudWatch `REPORT` lines. Reproduce them, do not trust
them: they are one account, one region, one afternoon.

| | n | min | p50 | p90 | max |
|---|---|---|---|---|---|
| Cold start (`Init Duration`) | 47 | 163.5 ms | **207.4 ms** | 218.7 ms | 224.9 ms |
| Warm `GET /healthz` (`Duration`) | 72 | 0.94 ms | **1.10 ms** | 1.25 ms | 1.96 ms |
| Warm `POST /auth/login` (`Duration`) | 37 | 288 ms | **301 ms** | 313 ms | 532 ms |

Cold starts were forced by `update-function-configuration` (which replaces every
execution environment) followed by eight concurrent `GET /healthz`, repeated six
times. The warm rows are from the earlier run and were not re-measured.

Cold start has a history worth keeping, because each step was paid for
deliberately:

| | p50 | what changed |
|---|---|---|
| before Secrets Manager | 91.4 ms | signing keys came from environment variables — and `lambda:GetFunction` could therefore read them and forge a token |
| two secrets, two fetches | 235.0 ms | keys moved into Secrets Manager, fetched at init; two ARNs meant two sequential `GetSecretValue` calls |
| one secret, one fetch | **207.4 ms** | both keys in one JSON secret, so the per-secret cache serves the second knob for free |

Reading them:

- **Collapsing the two fetches into one is worth ~28 ms at p50, not ~140 ms.**
  Measured back to back on the same stack the same evening: p50 235.0 → 207.4,
  mean 236.5 → 196.5, max 295.2 → 224.9. The tail moves more than the median,
  which is the shape you would expect from removing a second network round trip.
  The remaining ~116 ms over the pre-Secrets-Manager 91 ms is **not** the number
  of calls — it is the first call: loading the credential chain and standing up
  a TLS connection to Secrets Manager. A third fetch would be cheap and a zeroth
  would be free; there is no second round trip left to remove.
- **CloudTrail says the fetch count is what the latency implies.** Over the 24
  baseline cold starts, `GetSecretValue` appears 24 times against each of the two
  old secrets. Over the 47 cold starts after, it appears once per cold start
  against `JwtSigningSecrets` and never against the seed.
- **Cold start is ~207 ms of `Init Duration`, and the first request then runs in
  1.6–3.8 ms.** `New()` does the whole expensive path during init — config load
  and validation, secret resolution, the AWS client and its connection pool, the
  store, the auth core, the routing table — so the invocation that pays for the
  cold start is not also the one that builds everything. Init is billed.
- **Warm `/healthz` at ~1.1 ms is the floor** — event decode, route, respond,
  encode. That is the overhead `internal/lambdahttp` adds, with no store call in
  it.
- **`/auth/login` at ~301 ms is bcrypt, not the platform.** The imported core
  hashes at a fixed cost of 10 and that dominates everything else in the
  request. Raising `MemorySize` to 1024 gives the function more CPU and roughly
  halves this for about the same GB-ms bill — the one tuning knob that actually
  moves login latency. The 532 ms outlier is the first login in the run.
- Max memory used was 26–38 MB against the 512 MB configured. Memory here buys
  CPU, not headroom.

End-to-end from a laptop in Europe, including TLS and internet RTT: ~0.14 s warm
`/healthz`, ~0.46 s warm login, 0.37–0.58 s for a request that hits a cold
start.

## Troubleshooting

### `Circular dependency between resources: [HttpApiStage, AuthFunctionRootPermission, HttpApi, AuthFunction, AuthFunctionProxyPermission]`

The changeset fails before a single resource is created. This is the one failure
a first deployment of this template used to hit, and the fix is already in
`template.yaml` — it is documented here because the same mistake is easy to
reintroduce.

The cause is a function environment variable that references the API:

```yaml
# DON'T
AWESOME_AUTH_DEPLOYMENT_PUBLIC_URL: !Sub 'https://${HttpApi}.execute-api.${AWS::Region}.${AWS::URLSuffix}'
```

SAM generates the API's OpenAPI `DefinitionBody` from the function's events, and
every `x-amazon-apigateway-integration` in it names the function's ARN. So the
API already depends on the function; pointing the function at the API closes the
loop. It applies to anything you might want in the environment — the API id, the
endpoint, the stage ARN.

Get the value some other way instead:

- **An `Outputs` entry may reference `HttpApi` freely.** Outputs resolve after
  every resource exists, which is why `ApiEndpoint` works.
- **The request already carries it.** In payload format 2.0,
  `requestContext.domainName` and `requestContext.stage` give the function its
  own public origin per invocation, with no template reference at all.
- **Or just set it explicitly**, which is what this template does: `PublicUrl`
  is empty by default and the variable is omitted entirely
  (`!Ref 'AWS::NoValue'`). Nothing is lost, because `deployment.publicUrl` has
  exactly one consumer — refuse-to-start rule RS-2 — and RS-2 only matters on a
  custom domain, where you are setting `PublicUrl` anyway.

### `Runtime.InvalidEntrypoint` on every invocation

The zip has no executable named exactly `bootstrap` at its root.
`scripts/build-lambda.sh` gets this right and `scripts/deploy.sh` checks it
before uploading; you only see this if you built the artifact by hand.

### The function starts, then exits, and every request 500s

A refuse-to-start rule rejected the configuration. The reason is in the log
group as a `configuration error` line carrying the `rule`, `path` and a
`remedy` — one line per diagnostic, each self-contained. `RS-2` on a fresh
stack means `AllowInsecureCookieMode` got set to `false` without a custom
domain in `PublicUrl`.

`RS-1` with `"the access and refresh signing secrets are identical"` is the one
to expect when bringing your own: two references that resolve to the same bytes.
The easy way to cause it is to point `JwtAccessSecretArn` at a bare-string
secret and `JwtRefreshSecretArn` at a JSON secret whose selected key happens to
hold a copy of that same string. The reference in the diagnostic's `source` field
tells you which of the two to change. Note that it fails at init, not at the
first login — which is the point of a refuse-to-start rule.

## Before you put real users behind it

The defaults are tuned for "works in five minutes on a raw execute-api URL",
which is not the same as production-ready. Three things to change:

1. **Attach a custom domain** and set `PublicUrl` to it, then set
   `AllowInsecureCookieMode=false`. On an execute-api URL the service cannot
   issue hardened cookies — the stage path is not `/` and the registrable domain
   is shared with every other AWS account. The template's header comment spells
   this out; the governing knob is `cookies.allowInsecureCookieMode`
   (`AWESOME_AUTH_COOKIES_ALLOW_INSECURE_COOKIE_MODE`), enforced by refuse-to-start
   rule RS-2. Bearer clients (`X-Auth-Strategy: bearer`) are unaffected.
2. **`DeploymentEnvironment=production`**, which turns on the strict
   refuse-to-start rules in `docs/spec/config-schema.md` §2.
3. **`EnableDeletionProtection=true`**, and change the table's `DeletionPolicy`
   and `UpdateReplacePolicy` to `Retain` by hand — they take no intrinsic
   functions, so they cannot be parameterised.

The signing secrets used to be the fourth item here, because CloudFormation
substituted their values into the function's environment and `lambda:GetFunction`
read them out in cleartext. It is not a tradeoff any more: the function receives
ARNs and fetches the values itself. See
[Where the signing secrets live](#where-the-signing-secrets-live). What remains
true is that `secretsmanager:GetSecretValue` on that ARN, however granted, is
equivalent to being able to mint a token for any user — audit who holds it, and
turn on CloudTrail data events for the secret if you want to see reads. Read the
[rotation trade-off](#rotating) before you rely on the default layout: both keys
in one secret means both keys rotate together.

Also worth knowing: the DynamoDB driver currently backs `users`, `sessions` and
`tokens` only. Turning on any other `stores.enable.*` key makes the function
refuse to start rather than serve a route that would fail on the wire.

### Upgrading an existing stack to the one-secret layout

Deploying this template over a stack that predates it **replaces the signing
keys**, because the old `JwtAccessSecret` and `JwtRefreshSecret` resources are
gone from the template and `JwtSigningSecrets` is new. CloudFormation creates the
new secret, repoints the function and deletes the old two. Every access and
refresh token issued before the update stops verifying, so every session ends —
users log in again. Nothing else is touched: the table, its data and the API
endpoint all survive. If that matters, drain traffic first, or pin the old keys
by passing them as `JwtAccessSecretArn` / `JwtRefreshSecretArn` before the
upgrade, which keeps them alive as bring-your-own secrets at the cost of the
second fetch.

## Tear it down

```sh
./scripts/teardown.sh --profile <profile> --region <region> --stack-name <stack>
```

It asks you to type the stack name, then deletes the stack and waits. Three
things need a flag because nothing should delete them by surprise:

- `--disable-deletion-protection` — required if you deployed with
  `EnableDeletionProtection=true`, otherwise the stack delete fails on the table
  and rolls back.
- `--purge-secrets` — CloudFormation *schedules* secret deletion with a 30-day
  recovery window and bills for it until then. This force-deletes both
  `JwtSigningSecrets` and `JwtRefreshSecretSeed` immediately. Irreversible, and
  without `JwtSigningSecrets` no previously issued token can ever be verified
  again. It discovers them by resource type, so a bring-your-own stack — which
  creates neither — has nothing to purge and yours are left alone.
- `--delete-artifact-bucket` — empties every version and delete marker, then
  removes the bucket.

**The table and everything in it goes with the stack.** `DeletionPolicy` is left
at `Delete` so a quickstart stays disposable; PITR does not survive the table.
Export first if any of that data matters.
