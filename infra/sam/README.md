# SAM quickstart

An auth service in your own AWS account: one HTTP API, one Lambda, one DynamoDB
table. `template.yaml` is a SAM template (`AWS::Serverless-2016-10-31`), but
**you do not need the SAM CLI** — the transform runs server-side in
CloudFormation, so the plain AWS CLI does the whole flow. The scripts below use
nothing else.

## Prerequisites

- **Docker**, to build the Lambda binary. The repo installs no Go toolchain on
  the host; `scripts/build-lambda.sh` compiles inside a pinned `golang` image.
- **AWS CLI v2**, with a named profile whose credentials can create IAM roles,
  Lambda functions, API Gateway APIs, DynamoDB tables, Secrets Manager secrets
  and an S3 bucket.

## What gets created

Inside the stack:

| Resource | Notes |
|---|---|
| `AWS::DynamoDB::Table` | Single table, `PK`/`SK` + one sparse GSI, on-demand billing with read/write ceilings, PITR on, TTL on `ttl`, streams `NEW_AND_OLD_IMAGES`. Key schema is `docs/spec/data-model.md` §2, not a guess. |
| `AWS::Serverless::Function` | `provided.al2023`, arm64, 512 MB, 10 s timeout. One function for the whole auth router — not function-per-route. |
| Its execution role | DynamoDB scoped to the table ARN and `…/index/GSI1`, plus `secretsmanager:GetSecretValue` on exactly the two signing-secret ARNs. See below. |
| `AWS::Serverless::HttpApi` | Payload format 2.0. `$default` stage, so the API serves at the domain root. |
| `AWS::Logs::LogGroup` | `/aws/lambda/<stack>-auth`, 14-day retention by default. |
| Two `AWS::SecretsManager::Secret` | 64-character HS256 signing secrets, generated by AWS. Never a template parameter, never in your shell history. Skipped for whichever of `JwtAccessSecretArn` / `JwtRefreshSecretArn` you supply. |

### Where the signing secrets live

The function's environment holds the secrets' **ARNs**, not their values. It
fetches each one itself at cold start, once per execution environment, and
caches it for that container's life — never per request.

```sh
aws lambda get-function-configuration --function-name <stack>-auth \
  --profile <profile> --region <region> \
  --query 'Environment.Variables' | grep SECRET
#   "AWESOME_AUTH_JWT_ACCESS_SECRET_SECRETSMANAGER": "arn:aws:secretsmanager:…"
```

That is the whole point of the `_SECRETSMANAGER` suffix: the unsuffixed
`AWESOME_AUTH_JWT_ACCESS_SECRET` is the *value*, is development-grade, and must
not appear in a deployed template. Anyone with `lambda:GetFunction` now learns
where the key lives — which they could learn from the stack anyway — and still
cannot sign a token without `secretsmanager:GetSecretValue` on that exact ARN.

**You never handle the value.** `GenerateSecretString` creates it inside AWS.
There is no command to run, nothing to paste, nothing in your shell history.

Bringing your own secret is one parameter and no exposure either:

```sh
./scripts/deploy.sh --profile <profile> --region <region> \
  --parameter JwtAccessSecretArn=arn:aws:secretsmanager:<region>:<account>:secret:my/jwt-AbCdEf
```

It must be an ARN, not a name — the same value is the IAM policy's `Resource`,
and a bare name there is not a valid ARN. If your secret stores a JSON document
rather than a bare string, append the key: `…:secret:my/jwt-AbCdEf#accessTokenSecret`.
The `#` selector is stripped before the ARN reaches IAM.

Rotating is `aws secretsmanager put-secret-value`; the next cold start picks it
up, with no redeploy. Tokens signed with the old value stop verifying, which is
what rotation means.

SSM SecureString works too — set `AWESOME_AUTH_JWT_ACCESS_SECRET_SSM_PARAMETER`
instead — but this template does not grant `ssm:GetParameter`, because nothing
in the default stack calls it. The statement to add is written out in the
template, next to the one that is granted.

Outside the stack, created by `scripts/deploy.sh`: a private, encrypted,
versioned S3 bucket named `awesome-lambda-auth-artifacts-<account-id>-<region>`
to upload the Lambda zip to. It is not stack-managed, so teardown only removes
it if you ask.

### The IAM policy is the point

The function's policy grants exactly the seven DynamoDB item actions the store
calls, on exactly two ARNs — the table and its one index — and nothing else. No
`Resource: "*"`, no `dynamodb:*`, no `Scan`, no `DescribeTable`, not even `ConditionCheckItem`,
because nothing in the current store puts a bare condition check into a
transaction. If you copy one thing out of this template into your own stack,
copy that block. A wildcard in an auth service's execution role is a bad example
that propagates.

The second statement is one action — `secretsmanager:GetSecretValue` — on the
two signing-secret ARNs. Not even the `:*` suffix AWS documentation habitually
appends: a full ARN including the six-character suffix Secrets Manager
generates is an exact match, and the wildcard form would also match every
future secret whose name shares the prefix. No `kms:Decrypt`, because the
AWS-managed `aws/secretsmanager` key needs no grant on the caller; a
customer-managed key does.

## Cost at rest

Idle, with no traffic and an empty table, this stack costs roughly **$0.80 a
month**, and all of it is the two Secrets Manager secrets at $0.40 each. Every
other resource is either free at rest or billed per request:

- DynamoDB on-demand: no hourly charge. Storage ~$0.25–0.31 per GB-month
  depending on region, plus about the same again for PITR. An empty table is
  effectively free.
- Lambda, HTTP API, DynamoDB streams (enabled but unconsumed): $0 when idle.
- CloudWatch Logs: ~$0.50 per GB ingested and ~$0.03 per GB-month stored.
  Retention is capped at 14 days by default because never-expire is a bill that
  only grows.
- S3 artifact bucket: a few megabytes per deployed version. Cents.

Under traffic the shape is roughly $1 per million API requests, $0.20 per
million Lambda invocations plus GB-seconds, and $1.25 per million DynamoDB
writes / $0.25 per million reads. Those are order-of-magnitude figures from the
public pricing pages and vary by region — check the current numbers before
budgeting on them.

`MaxReadRequestUnits` / `MaxWriteRequestUnits` default to 200 each. That is a
deliberate cap: a credential-stuffing run against `/login` becomes a DynamoDB
bill before it becomes an outage. Raise it on purpose, and alarm on it.

## Deploy

```sh
# 1. build the artifact (arm64, `bootstrap` at the archive root, reproducible)
./scripts/build-lambda.sh

# 2. package + deploy. --profile and --region are required and have no defaults.
./scripts/deploy.sh --profile <your-profile> --region <your-region>
```

`--build` folds step 1 into step 2. The script prints the account it resolved
and asks for confirmation before it touches anything; `--yes` skips the prompt
for CI.

Under the hood it is just:

```sh
aws cloudformation package \
  --template-file infra/sam/template.yaml \
  --s3-bucket <bucket> --s3-prefix <stack> \
  --output-template-file dist/packaged.yaml \
  --profile <profile> --region <region>

aws cloudformation deploy \
  --template-file dist/packaged.yaml \
  --stack-name <stack> \
  --capabilities CAPABILITY_IAM CAPABILITY_AUTO_EXPAND \
  --profile <profile> --region <region>
```

`CAPABILITY_AUTO_EXPAND` is what lets CloudFormation run the SAM transform.

Validate a template edit without deploying:

```sh
aws cloudformation validate-template \
  --template-body file://infra/sam/template.yaml \
  --profile <profile> --region <region>
```

Note what that does **not** do: it checks the template document, not the
expanded stack, because the SAM transform has not run yet. It will catch a
syntax error or a bad intrinsic; it will not catch an invalid Lambda property.

### Smoke test

```sh
curl -sS "$(aws cloudformation describe-stacks --stack-name <stack> \
  --query "Stacks[0].Outputs[?OutputKey=='ApiEndpoint'].OutputValue" --output text \
  --profile <profile> --region <region>)/healthz"
```

Outputs are `ApiEndpoint`, `TableName` and `FunctionName`. Auth routes live
under `<ApiEndpoint><ApiPrefix>`, i.e. `/auth` by default.

## Measured on a real deployment

Numbers from a `$default`-stage stack in `eu-west-1`, arm64 / 512 MB, defaults
otherwise, read from CloudWatch `REPORT` lines. Reproduce them, do not trust
them: they are one account, one region, one afternoon.

| | n | min | p50 | p90 | max |
|---|---|---|---|---|---|
| Cold start (`Init Duration`) | 6 | 82.0 ms | **91.4 ms** | 94.0 ms | 96.4 ms |
| Warm `GET /healthz` (`Duration`) | 72 | 0.94 ms | **1.10 ms** | 1.25 ms | 1.96 ms |
| Warm `POST /auth/login` (`Duration`) | 37 | 288 ms | **301 ms** | 313 ms | 532 ms |

Reading them:

- **Cold start is ~91 ms of `Init Duration`, and the first request then runs in
  1.6–3.8 ms.** `New()` does the whole expensive path during init — config load
  and validation, secret resolution, the AWS client and its connection pool, the
  store, the auth core, the routing table — so the invocation that pays for the
  cold start is not also the one that builds everything. Init is billed: those
  invocations bill 84–99 ms against a 1.6 ms handler.
- **Warm `/healthz` at ~1.1 ms is the floor** — event decode, route, respond,
  encode. That is the overhead `internal/lambdahttp` adds, with no store call in
  it.
- **`/auth/login` at ~301 ms is bcrypt, not the platform.** The imported core
  hashes at a fixed cost of 10 and that dominates everything else in the
  request. Raising `MemorySize` to 1024 gives the function more CPU and roughly
  halves this for about the same GB-ms bill — the one tuning knob that actually
  moves login latency. The 532 ms outlier is the first login in the run.
- Max memory used was 26–38 MB against the 512 MB configured. Memory here buys
  CPU, not headroom.

End-to-end from a laptop in Europe, including TLS and internet RTT: ~0.14 s warm
`/healthz`, ~0.46 s warm login, 0.37–0.58 s for a request that hits a cold
start.

## Troubleshooting

### `Circular dependency between resources: [HttpApiStage, AuthFunctionRootPermission, HttpApi, AuthFunction, AuthFunctionProxyPermission]`

The changeset fails before a single resource is created. This is the one failure
a first deployment of this template used to hit, and the fix is already in
`template.yaml` — it is documented here because the same mistake is easy to
reintroduce.

The cause is a function environment variable that references the API:

```yaml
# DON'T
AWESOME_AUTH_DEPLOYMENT_PUBLIC_URL: !Sub 'https://${HttpApi}.execute-api.${AWS::Region}.${AWS::URLSuffix}'
```

SAM generates the API's OpenAPI `DefinitionBody` from the function's events, and
every `x-amazon-apigateway-integration` in it names the function's ARN. So the
API already depends on the function; pointing the function at the API closes the
loop. It applies to anything you might want in the environment — the API id, the
endpoint, the stage ARN.

Get the value some other way instead:

- **An `Outputs` entry may reference `HttpApi` freely.** Outputs resolve after
  every resource exists, which is why `ApiEndpoint` works.
- **The request already carries it.** In payload format 2.0,
  `requestContext.domainName` and `requestContext.stage` give the function its
  own public origin per invocation, with no template reference at all.
- **Or just set it explicitly**, which is what this template does: `PublicUrl`
  is empty by default and the variable is omitted entirely
  (`!Ref 'AWS::NoValue'`). Nothing is lost, because `deployment.publicUrl` has
  exactly one consumer — refuse-to-start rule RS-2 — and RS-2 only matters on a
  custom domain, where you are setting `PublicUrl` anyway.

### `Runtime.InvalidEntrypoint` on every invocation

The zip has no executable named exactly `bootstrap` at its root.
`scripts/build-lambda.sh` gets this right and `scripts/deploy.sh` checks it
before uploading; you only see this if you built the artifact by hand.

### The function starts, then exits, and every request 500s

A refuse-to-start rule rejected the configuration. The reason is in the log
group as a `configuration error` line carrying the `rule`, `path` and a
`remedy` — one line per diagnostic, each self-contained. `RS-2` on a fresh
stack means `AllowInsecureCookieMode` got set to `false` without a custom
domain in `PublicUrl`.

## Before you put real users behind it

The defaults are tuned for "works in five minutes on a raw execute-api URL",
which is not the same as production-ready. Three things to change:

1. **Attach a custom domain** and set `PublicUrl` to it, then set
   `AllowInsecureCookieMode=false`. On an execute-api URL the service cannot
   issue hardened cookies — the stage path is not `/` and the registrable domain
   is shared with every other AWS account. The template's header comment spells
   this out; the governing knob is `cookies.allowInsecureCookieMode`
   (`AWESOME_AUTH_COOKIES_ALLOW_INSECURE_COOKIE_MODE`), enforced by refuse-to-start
   rule RS-2. Bearer clients (`X-Auth-Strategy: bearer`) are unaffected.
2. **`DeploymentEnvironment=production`**, which turns on the strict
   refuse-to-start rules in `docs/spec/config-schema.md` §2.
3. **`EnableDeletionProtection=true`**, and change the table's `DeletionPolicy`
   and `UpdateReplacePolicy` to `Retain` by hand — they take no intrinsic
   functions, so they cannot be parameterised.

The signing secrets used to be the fourth item here, because CloudFormation
substituted their values into the function's environment and `lambda:GetFunction`
read them out in cleartext. It is not a tradeoff any more: the function receives
ARNs and fetches the values itself. See
[Where the signing secrets live](#where-the-signing-secrets-live). What remains
true is that `secretsmanager:GetSecretValue` on those ARNs, however granted, is
equivalent to being able to mint a token for any user — audit who holds it, and
turn on CloudTrail data events for the two secrets if you want to see reads.

Also worth knowing: the DynamoDB driver currently backs `users`, `sessions` and
`tokens` only. Turning on any other `stores.enable.*` key makes the function
refuse to start rather than serve a route that would fail on the wire.

## Tear it down

```sh
./scripts/teardown.sh --profile <profile> --region <region> --stack-name <stack>
```

It asks you to type the stack name, then deletes the stack and waits. Three
things need a flag because nothing should delete them by surprise:

- `--disable-deletion-protection` — required if you deployed with
  `EnableDeletionProtection=true`, otherwise the stack delete fails on the table
  and rolls back.
- `--purge-secrets` — CloudFormation *schedules* secret deletion with a 30-day
  recovery window and bills for it until then. This force-deletes both
  immediately. Irreversible, and without those secrets no previously issued
  token can ever be verified again.
- `--delete-artifact-bucket` — empties every version and delete marker, then
  removes the bucket.

**The table and everything in it goes with the stack.** `DeletionPolicy` is left
at `Delete` so a quickstart stays disposable; PITR does not survive the table.
Export first if any of that data matters.
