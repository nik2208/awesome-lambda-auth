# Parity gap — awesome-node-auth (reference) vs awesome-go-auth

**Purpose.** This document quantifies how much a Go-based Lambda port would inherit for free from `awesome-go-auth` versus what it would have to build, against the family reference `awesome-node-auth` v1.9.0. It is one of the inputs to the **Phase 0 language decision**. Every claim is code-verified at the pinned commits listed in [Provenance](#provenance); file:line references resolve against those SHAs (Node paths relative to the awesome-node-auth root, Go paths relative to the awesome-go-auth root).

The one-sentence architectural summary: the Go port is a **service-layer library** (`Service` methods on a struct) with thin optional HTTP adapters, whereas the Node reference is **router-first** (four Express routers exposing the full wire contract). Most capabilities therefore exist in Go as callable, tested functions but have **no HTTP surface**, and the five routes that do exist diverge from the family wire contract in cookie names, JSON casing, response envelopes, and error bodies.

The service layer is the strong half of the Go port: ~17 capabilities have working, tested Go business logic awaiting HTTP glue. The wire layer is the weak half: nothing that goes over HTTP today matches the family contract.

Derived roll-up of the 31 capability rows and their gap-closure costs (sizing defined in [How to read the matrix](#how-to-read-the-matrix)):

- **0 rows are inheritable as-is over HTTP.** Every mounted route diverges in at least one of: response envelope/casing, cookie names, error bodies.
- **3 L-sized gaps** — OAuth HTTP layer + state validation (row 13), admin surface (row 19), tools surface (row 20). These are missing subsystems, not adjustments.
- **15 M-sized gaps** — new mechanisms within existing modules (token format, cookie/CSRF wiring, tempToken challenge flows, EmailVerificationMode, mailer wiring, IdP ops, API-key store, SSE auth, config surface, persistent stores).
- **11 S-sized gaps + 2 split rows (6, 7)** — renames, envelope fixes, and HTTP glue over already-tested service logic.

## Reading the numbers for the Phase 0 decision

Three observations frame what these numbers mean for a Lambda port:

**What Go inherits for free is business logic, not contract.** Roughly 17 of 31 capabilities have working, well-tested Go implementations (stores, token flows, TOTP, RBAC, tenancy, API keys). That is real, non-trivial code a port would not rewrite. But none of it is reachable over HTTP in the family shape, and the family shape is precisely what the three existing clients (Angular, Flutter, served auth.js) pin — see the [client-contract cross-check](#client-contract-cross-check). A Lambda port's deliverable *is* the wire contract; the part Go has already built is the part that was never the hard part to specify.

**The divergences are load-bearing, not cosmetic.** The custom 2-part token format (row 25) breaks every client-side claim decode and any gateway JWT authorizer; the missing `SESSION_REVOKED` error code (row 3) breaks client refresh/logout state machines; the cookie names (row 26) silently log out every migrating session. These sit *under* the route-surface gap: mounting 30 more routes on top of the current token and cookie layer would produce 30 more incompatible routes.

**The uplift is upstream work, not port work.** Closing the gap means changing `awesome-go-auth` itself (issues #6–#16 below) rather than forking its behavior inside a Lambda wrapper. The dependency chain — DTOs → JWTs → route surface → everything else — is serialized: items 1–3 of the [uplift list](#what-choosing-go-actually-costs) gate the other eight.

## How to read the matrix

- **Verdict** — ✅ full (implemented and wire-compatible) · ⚠️ partial (subdivided: *diverges* = has HTTP or a client-facing shape that doesn't match the reference; *service-only* = correct-ish business logic, no HTTP surface) · ❌ absent.
- **Cost** — t-shirt size to close the gap to reference behavior: **S** = wiring/renaming over existing tested logic; **M** = a new mechanism or contract change within one module; **L** = a whole missing subsystem.
- Row numbers follow the underlying extract (`_extract/08-go-parity.md`) for traceability.
- `[MISMATCH: …]` flags a verified wire-contract break; `[UNTESTED]` means no Go test exercises the code path.

**Pattern.** A mixed group with the two L-sized holes (admin: 0 of 50 routes; tools: 0 of 7 routes) and, at the other extreme, the port's best module — API keys, whose key format, prefix scheme, and `X-Api-Key` header already match the reference and which carries 37 tests. The recurring failure mode here is *unwired completeness*: the mailer, the SSE handler, the OpenAPI generator, the telemetry store, and the event bus all exist as working components that nothing mounts or calls. Four of the ten rows carry [UNTESTED] for their entire module (idp, mailer, openapi, ui), and none of them run in CI because there is no CI (issue #13).

## The single deepest wire break: token builders side by side

Node (src/services/token.service.ts:20-29) — standard JWTs, split secrets:

```ts
const accessToken = jwt.sign(claims, config.accessTokenSecret,
  { expiresIn: config.accessTokenExpiresIn ?? '15m' });
const refreshToken = jwt.sign(claims, config.refreshTokenSecret,
  { expiresIn: config.refreshTokenExpiresIn ?? '7d' });
```

Go (token.go:59-65) — custom 2-part format, one secret:

```go
raw, err := json.Marshal(payloadClaims)
...
payload := base64.RawURLEncoding.EncodeToString(raw)
sig := sign(payload, s.cfg.Secret)          // HMAC-SHA256, security.go:69-73
return payload + "." + sig, expiresAt, nil  // <payload>.<sig> — no JOSE header
```

Everything downstream of a token — clients decoding claims, `auth.js`, gateway JWT authorizers, the Angular/Flutter interceptors — breaks on the Go format (issue #8). Note the irony pinned in idp.go:282-301: the Go repo already contains a correct stdlib 3-part JWT builder (`buildRS256JWT`), used only for ID tokens.

## What choosing Go actually costs

If Go were chosen as the Lambda base, `awesome-go-auth` would need the following upstream uplift before (or while) the port is built. Ordered by dependency — earlier items are prerequisites for later ones; each maps to an issue filed on nik2208/awesome-go-auth.

1. **[#6](https://github.com/nik2208/awesome-go-auth/issues/6) — Response DTOs / stop serializing secrets** (models.go has no JSON tags; every mounted route leaks `PasswordHash`, `TOTPSecret`, `*TokenHash`). Security-critical and a prerequisite for any casing fix; do first.
2. **[#8](https://github.com/nik2208/awesome-go-auth/issues/8) — Replace the custom 2-part token with standard HS256 JWTs** (token.go:22-94), reference claim set + split access/refresh secrets. Everything client-facing depends on it.
3. **[#9](https://github.com/nik2208/awesome-go-auth/issues/9) — Mount the family route surface** (~30 missing routes; service layer already exists for most). Encode the contract while doing it: 401 `{code:"SESSION_REVOKED"}`, `X-Auth-Strategy: bearer` top-level tokens, unwrapped `/me`, `{sessions:[…]}`, `{linkedAccounts:[…]}`, magic-link `mode` defaulting to `login`, cookie names `accessToken`/`refreshToken`/`csrf-token` with `__Host-`/`__Secure-` resolution and `/refresh`-scoped refresh path.
4. **[#7](https://github.com/nik2208/awesome-go-auth/issues/7) — `EmailVerificationMode` none/lazy/strict** (Register hardcodes verified; the verification flow is dead code on the default path).
5. **[#10](https://github.com/nik2208/awesome-go-auth/issues/10) — OAuth state validation (HMAC-signed state), PKCE (S256), wire or remove `PendingLinkStore`** (enables `link-request`/`link-verify` from #9).
6. **[#14](https://github.com/nik2208/awesome-go-auth/issues/14) — IdP key material from config (PEM) + `AuthCodeStore` interface + key-set rotation** (currently ephemeral per-process RSA + in-process codes).
7. **[#15](https://github.com/nik2208/awesome-go-auth/issues/15) — Outbound webhook contract**: rename to `X-Webhook-Signature`/`X-Webhook-Event`/`X-Webhook-Delivery`/`X-Webhook-Timestamp`, add bounded retry with exponential backoff, drop fire-and-forget goroutine.
8. **[#11](https://github.com/nik2208/awesome-go-auth/issues/11) — Vendor the reference UI assets byte-identical** (auth.js 32,002 B, blob-SHA-comparable in CI, as the Rust port does) — sequenced strictly after #8 and #9, since the vendored SDK requires the reference wire contract.
9. **[#12](https://github.com/nik2208/awesome-go-auth/issues/12) — Compilable examples + at least one persistent store** (drop `//go:build ignore`, fix fictional adapter APIs, `go mod tidy` the unused mongo driver).
10. **[#13](https://github.com/nik2208/awesome-go-auth/issues/13) — CI** (gofmt/vet/build/test -race + example compilation) and cut the first real tag so the CHANGELOG's `[0.1.0]` exists.
11. **[#16](https://github.com/nik2208/awesome-go-auth/issues/16) — Docs truth pass** (README parity table, README_DETAILED adapter API and config defaults — refresh 30d vs documented 7d, ClockSkew 30s vs 5s, EmailChangeTTL 1h vs 24h) and regenerate openapi.go from the real surface once #9 lands.

Upstream-tracked but outside the #6–#16 band: **[#4](https://github.com/nik2208/awesome-go-auth/issues/4)** (auto-publish `identity.*` events from `Service` — a Node **v1.10** feature; at the pinned v1.9.0 reference neither implementation publishes from core, so it is parity-neutral for this matrix) and **[#5](https://github.com/nik2208/awesome-go-auth/issues/5)** (the audit meta-checklist these issues descend from).
